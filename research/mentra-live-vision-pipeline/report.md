# Make one Mac hub tame Mentra Live

**Build this as a Mac-centred hub in which the glasses supply slow context and the wristband and muscle sensor supply every time-critical trigger.** Mentra Live has no documented way to push pixels to a Mac over Bluetooth. The realistic routes are an unmanaged RTMP stream to an endpoint you run on the Mac, a managed WebRTC (WHIP) stream through Mentra's cloud, or one-off `requestPhoto` stills that take seconds over Bluetooth ([RTMP guide](https://docs.mentraglass.com/camera/rtmp-streaming), [camera streaming](https://docs.mentraglass.com/mentra-live/camera-streaming), [PR #4574](https://github.com/Mentra-Community/MentraOS/pull/4574)). **No glass-to-screen latency for Mentra Live has been measured anywhere we could find, and the team's 300-800 ms figure is an unverified plan, not a fact.** Whether Mentra Live has a readable IMU is also unconfirmed, so head pose must come from the camera itself. That shapes every design choice below. Fingertip pointing should be built as region picking (AprilTag markers, a homography, MediaPipe hand landmarks, One Euro smoothing), not as a precise mouse. The "squeeze the screen like paper" demo should be triggered by the ESP32 muscle sensor, with the glasses only choosing the target, and its display half can be built and shown before any sensor works. Lamps should be registered once rather than recognised generically, and driven through WLED, Tasmota, Shelly or Home Assistant over local HTTP. The gimbal should turn only to guests who gave written consent, after a push-to-talk tap on the band, and the guest-matching step has a biometric-free fallback. Each section ends with what is unverified, and a register of open risks follows the build order.

**Band number.** The kit requires each team to use its own band number ([AGENTS.md](../../AGENTS.md)). No number was given for this research, so every sketch here uses a placeholder constant `TEAM_BAND` that the team must fill in. The number goes in one place, is checked against `band.number` after connecting, and is never copied from an example. The code must never scan unfiltered or try another number.

## Frames reach the Mac by RTMP, WHIP or slow stills, and the Mac owns the band

**Topology.** The glasses talk to a phone running the Mentra app or a Bluetooth-SDK app, and the glasses join Wi-Fi using credentials sent over Bluetooth (`sendWifiCredentials`) ([Bluetooth SDK API](https://docs.mentraglass.com/bluetooth-sdk/api-reference)). The Vexo band is a Bluetooth peripheral that accepts **one connection at a time**, and the dashboard counts as a connection, so the Mac hub must be the band's only Bluetooth client and the dashboard tab must be closed while it runs ([AGENTS.md rule 7](../../AGENTS.md), [contract.md](../../contract/contract.md)). The kit's Python library (bleak plus `vexo_open.sync`) already filters by exact name, rejects the wrong band with `wrong-band`, reconnects and sets the band's clock from the Mac, which gives the hub a common clock with the band for free ([api.md](../../docs/api.md)). The kit supplies no ESP32 client code, and an ESP32 holding the band would lock the Mac out, so the ESP32 should talk only to its EMG sensor and to the Mac as a Wi-Fi WebSocket client (an inference from the kit's single-connection rule; no ESP32-to-band test exists). A WebSocket was the lowest-latency and most reliable option in the one ESP32 comparison found ([JATI 2026](https://ejournal.itn.ac.id/jati/article/view/18056)), and ESP32 servers degrade with more than three WebSocket clients ([esp32.com thread](https://esp32.com/viewtopic.php?p=151689)), so the ESP32 should be a client of the Mac's server, not the other way round. The hub is one asyncio process that timestamps everything on arrival and appends every message to a JSON-lines log. That log is what later lets the team measure delays and tune thresholds.

**Three ways to get pixels.** Mentra documents two streaming modes. Managed streaming goes through Mentra's cloud: WHIP gives sub-second WebRTC playback with no recording, while the default SRT gives 10-20 s latency with HLS/DASH ([streaming docs](https://docs.mentraglass.com/app-devs/core-concepts/stream), [camera streaming](https://docs.mentraglass.com/mentra-live/camera-streaming)). Unmanaged streaming publishes directly to a URL you own, "can work on local networks", but takes exclusive control of the camera and allows one such stream per device ([RTMP guide](https://docs.mentraglass.com/camera/rtmp-streaming), [unmanaged extension](https://docs.mentraglass.com/cloud-architecture/managers/unmanaged-streaming-extension)). The notes' inference, which the docs do not prescribe, is to run MediaMTX or `ffmpeg -listen 1` on the Mac, give the glasses `rtmp://<mac-lan-ip>:1935/live/<key>`, and read frames with OpenCV or PyAV. Generic HLS runs 25-30 s glass-to-glass and low-latency HLS about 5 s ([Mux](https://www.mux.com/docs/live-streaming-latency)); a local RTMP receiver is expected to land at roughly 1-3 s, but that is an estimate. Stills are the slow path: a 264,812-byte JPEG took 5,779 ms over Bluetooth GATT (about 3.5 s over CoC), measured only to the glasses-side acknowledgement, and truncated-frame bugs have stalled transfers 9-32 s ([PR #4574](https://github.com/Mentra-Community/MentraOS/pull/4574), [PR #4349](https://github.com/Mentra-Community/MentraOS/pull/4349)). Stills suit "snapshot on trigger", for example one frame when a lamp is selected, and never continuous tracking. Because an unmanaged stream blocks other camera use, plan to take stills from the video stream rather than mixing the two.

**SDK choice.** Three SDK generations are documented at once. The cloud TypeScript SDK (`@mentra/sdk`) is the simplest way to reach your own server. MentraOS 3.0 miniapps run on the phone, support only local testing, and have no distribution path yet ([distribution](https://docs.mentraglass.com/app-devs/getting-started/distribution), [local development](https://docs.mentraglass.com/app-devs/getting-started/deployment/local-development)). The Bluetooth SDK (`@mentra/bluetooth-sdk`) needs a physical phone, a development build, and an SDK version matched to the glasses release ([npm](https://npmjs.com/package/@mentra/bluetooth-sdk), [Mentra Live docs](https://docs.mentraglass.com/mentra-live/overview)). Version numbers disagree across sources (0.1.19, 0.1.20, 3.3.0), and one index claims a Cloud V2 publish path that contradicts the "no distribution" statement. Official docs were preferred. Registration, accounts and API keys could not be confirmed. For a hackathon, treat the first hour as a stream smoke test: get RTMP frames on the Mac, or fall back to the Mac webcam standing in for the glasses so the rest of the build is not blocked.

**What is unverified here.** Almost every Mentra fact in the notes comes from search-result summaries, because the docs hosts were blocked in the research sandbox. Default and maximum video resolution, frame rate, capture timestamps, battery and thermal behaviour while streaming, and whether RTMP works on a LAN with no internet are all unknown. The notes report a 119-degree field of view from most outlets and 112 degrees from one ([TechSpot](https://www.techspot.com/news/110955-new-mentra-live-smart-glasses-built-livestreaming-platforms.html?rand=98523), [9to5Google](https://9to5google.com/2026/01/15/mentra-live-smart-glasses-youtube-livestream/)). Either figure implies lens distortion that the screen homography must handle.

**Mentra IMU.** A `hasIMU` capability flag exists, and the official IMU guide says raw accelerometer streaming is currently for a different device, with subscriptions on other glasses succeeding but delivering nothing ([capabilities](https://docs.mentraglass.com/app-devs/reference/interfaces/capabilities), [IMU guide](https://docs.mentraglass.com/app-devs/core-concepts/imu), per search summary). One unofficial hardware note lists only an accelerometer on firmware v34.0 from a single source. **Read `session.capabilities` on the actual glasses before designing anything around head motion; until then assume there is no head-pose sensor.**

## Fingertip-to-cursor works as region picking, with markers doing the geometry

**Recommended chain.** The Mac shows four AprilTag or ArUco markers in the corners of a full-screen overlay. OpenCV's aruco module detects both families, with the caveat that AprilTag corner order differs from ArUco's ([OpenCV aruco](https://docs.opencv.org/4.x/de/d67/group__objdetect__aruco.html)). Each frame, `cv2.findHomography` on the marker corners (16 points from four tags, 12 if the finger hides one) maps camera pixels to screen points with no camera calibration, because the markers' screen positions are known. This is the same pattern as Microsoft Research's Visual Panel and as Sight Guide, which also tracks ORB features to keep the homography when the hand hides the corners ([MSR Visual Panel](https://microsoft.com/en-us/research/uploads/prod/2016/11/Vision-based-Interaction-with-Fingers-and-Papers.pdf), [Sight Guide](https://arxiv.org/pdf/2506.02676)). Hand landmarks come from MediaPipe Hand Landmarker (Apache-2.0 repo, 21 landmarks) run with one hand, in VIDEO mode, on a downscaled 640-960 px frame ([MediaPipe repo](https://github.com/google-ai-edge/mediapipe), [Labellerr guide](https://www.labellerr.com/blog/mediapipe-hand-tracking-egocentric-video/)). The index tip (landmark 8) goes through the homography, then a One Euro filter in screen pixels driven by real frame timestamps ([Casiez et al.](https://cristal.univ-lille.fr/~casiez/1euro)). Click is a pinch: thumb tip to index tip distance normalised by wrist-to-middle-knuckle distance, with separate enter and exit thresholds and a 2-3 frame debounce, as in Ultraleap's detector ([Ultraleap](https://docs.ultraleap.com/xr-and-tabletop/xr/unity/plugin/features/pinch-detector.html)). The notes' starting guess is enter about 0.3 and exit about 0.4 of palm size, and **that is a guess, not a published value.** Cursor injection uses Quartz CGEvent through pyobjc (or pyautogui). It needs the Accessibility permission for the host terminal, and ScreenCaptureKit needs Screen Recording permission ([Automate the Boring Stuff](https://automatetheboringstuff.com/2e/chapter20), [Apple forum](https://developer.apple.com/forums/thread/103992)). Build in a kill switch and freeze the cursor and release any held button if frames stall for roughly 300 ms.

**Why region picking, not mouse precision.** The homography is exact only for points on the screen plane. A fingertip hovering in front of the screen projects along the camera ray, not the eye's line of sight. The notes' own geometry, d_c x Z / (D - Z), gives about 1.2 cm of error for a 6 cm camera offset, 60 cm viewing distance and a 10 cm finger-to-screen gap, which is two or three icon widths (an unmeasured derivation). Add a 4-5 point calibration, offer a relative "trackpad" mode with pinch-to-clutch, and prefer large targets. Latency compounds this: the notes budget 150-500 ms motion-to-photon, dominated by the unmeasured stream, which is fine for dwell or pinch picks and poor for free-hand pointing. Use one thread that keeps only the newest frame, a worker for marker and hand inference, and a control loop that posts cursor events at a fixed rate. For optional semantic snapping ("the button I am pointing at"), the macOS Accessibility element-at-point call is the cheap first choice (the notes' own background knowledge, unverified). A vision-language model comes second and only once per pick, because grounding models placed predictions outside any UI element about 11% of the time in UiPath's report and must have coordinates rescaled from their resized image space ([UiPath](https://www.uipath.com/ai/research/screen-agent), [tianpan.co](https://tianpan.co/blog/2026-05-18-gui-agent-right-button-wrong-screen)). No measured latency for Claude, Gemini or GPT image grounding was found. The kit's own Python helper, `ai.py`, calls OpenAI only from Python and its key must never reach a web page ([AGENTS.md](../../AGENTS.md)); sending screen captures to any cloud model is a separate data transfer to check against consent.

**Prior art and gaps.** Many webcam air-mouse repos exist, but they map a fixed rectangle of the webcam frame, and none found does egocentric screen finding with a homography. slastra/pointer (MIT, Wayland-only) is worth reading for its One Euro tuning and debounce ([repo](https://github.com/slastra/pointer)). No published accuracy figure exists for egocentric fingertip pointing with MediaPipe or Apple Vision, and no AprilTag detection time at 1080p on Apple Silicon was found.

## The squeeze demo should fire from muscle, with the glasses only choosing the target

**Why EMG and not the glasses.** A grab or squeeze must be timed to tens of milliseconds, and the glasses path is slow and unmeasured. The notes therefore assign the trigger to the ESP32 and its EMG board, the band to motion context and fallback, and the glasses to retrospective context. An EMG board feeds the ESP32's ADC: the DFRobot Gravity sensor (SEN0240) passes 20-500 Hz, so sample at 1 kHz or more, and the MyoWare 2.0 offers raw, rectified and envelope outputs ([DFRobot](https://wiki.dfrobot.com/sen0240/), [SparkFun guide](https://cdn.sparkfun.com/assets/learn_tutorials/1/9/5/6/MyoWare_v2_AdvancedGuide-Updated.pdf)). Use ADC1 with the continuous driver, because on the classic ESP32 ADC2 conflicts with Wi-Fi; the notes did not verify the ESP32-S3 rules ([ESP-IDF ADC](https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32/api-reference/peripherals/adc_continuous.html)). Send batches every 20-50 ms, and decide `grab` and `release` on the ESP32 so a dropped packet cannot lose a trigger. One forearm channel can plausibly separate "clenched" from "relaxed" by an envelope threshold with hysteresis and a per-wearer calibration. A squeeze-like clench fits that, but it cannot separate a pinch from a fist; multi-channel armbands support pinch-class gestures in the literature, with accuracy falling across sessions and users ([Saarland EMG](https://umtl.cs.uni-saarland.de/paper_preprints/EMG.pdf), [Frontiers 2025](https://public-pages-files-2025.frontiersin.org/journals/neurorobotics/articles/10.3389/fnbot.2025.1531815/pdf)). **Electrode contact and placement are the biggest EMG risk.** Power the board from a battery or isolated USB, never from mains equipment, and the DFRobot page states it is not a medical device.

**What the band adds, and what it does not.** The band gives 6-axis motion (10-100 Hz in the simple stream, up to 416 Hz both sensors or 833 Hz one sensor over Bluetooth), seven gesture events, microphone loudness, and one LED ([contract.md](../../contract/contract.md), [AGENTS.md](../../AGENTS.md)). It has no magnetometer, no haptics, and **no pinch or grab detection in the kit**, which says so explicitly ([gesture-trainer README](../../projects/gesture-trainer/README.md)). Use it for a "throw" burst on gyro/accel (test thresholds on the team's own wrist; set `set_motion(accel_range=8)` first because the default 2 g range clips hard motions), as a fast-motion veto, and for `double-tap` as a no-ML fallback trigger. IMU-only pinch detection is shown on a custom 427 Hz wristband ([HOOV](https://arxiv.org/pdf/2303.07016)), but the cheap test is to log 30 pinches and 30 rest trials at the band's fastest accel setting and drop the idea if the difference is not visible. Yaw cannot be observed by a 6-axis IMU and drifts, so use the camera for where the hand is and the band for how it moves ([RUNE blog](https://ikouchiha47.github.io/rune/02-sensor-wars)). The LED can show "armed" or "grabbed" state but fails with `denied` whenever the microphone is on, so voice control and LED feedback must take turns.

**Surviving the glasses lag.** Keep a ring buffer of about two seconds of hub state. When a camera frame arrives, label it with its capture time (or the hub arrival time minus a measured delay) and look up what the hand was doing at `t_grab - delay`, never "latest". Never close a feedback loop through the glasses. Measure the delay with a visible event: a tap on a table gives a band `tap` timestamp and a visible impact frame, or a band LED flash seen by the camera (with the microphone off, uncertain by one 15-50 ms command round trip). Cross-correlating gyro magnitude with landmark speed is the Kalibr-style refinement ([Kalibr](https://github.com/ethz-asl/kalibr/wiki/Multi-IMU-and-IMU-intrinsic-calibration)). Report the delay as a distribution, not one number.

**The effect itself.** On `grab`, the hub captures one still of the display with ScreenCaptureKit (`SCScreenshotManager` on macOS 14+, or an `SCStream`), draws it on a mesh in Metal, SceneKit or three.js, and animates a crumple as vertex displacement and fold lines over 0.5-1 s ([Apple sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos.md)). It then sends the JPEG as one binary WebSocket message to a browser page on the projector machine, which plays the arrival or uncrumple animation on a `throw` or `release`. No source exists for the crumple animation, so this is design. Because it can be triggered from a keypress, **it is the safest first deliverable, and it still demos if every sensor fails.** The glasses' only job is target selection: which window or screen region the hand was over at grab time, looked up in the buffered past.

## Lamps and other Macs are chosen by registration, not by recognition

**Detection.** COCO's 80 classes include `tv` and `laptop` but not lamp, so lamps need an open-vocabulary detector or a small fine-tune ([Roboflow](https://blog.roboflow.com/microsoft-coco-classes/)). YOLO-World reports 35.4 LVIS AP at 52 FPS on a V100 ([arXiv](https://arxiv.org/abs/2401.17270v1)); YOLOE adds text prompts, visual prompts from an example box, and a prompt-free mode, and reports 27.9 LVIS AP at 305.8 FPS on a T4 for its small model ([YOLOE ICCV](https://iccv.thecvf.com/virtual/2025/poster/205)). OWLv2 is available in Hugging Face Transformers and is more accurate but with no latency figures found ([HF docs](https://huggingface.co/docs/transformers/model_doc/owlv2)); Grounding DINO 1.5 Edge runs 10.7 FPS on a Jetson Orin NX ([paper](https://arxiv.org/pdf/2405.10300)); Florence-2 has no reliable independent speed number. All speed figures are on GPUs and none is on an M-series Mac. The practical conclusion from the notes is that **the demo has a handful of known lamps, so register each one once** rather than trusting the word "lamp": the user looks at it, presses register, and picks its smart-home entity, and the app stores a visual-prompt embedding plus rough position. The closest published system, IRIS, pairs an egocentric camera with YOLO and DINOv2 for instance recognition at secondary-reported 95-98% accuracy ([IRIS](https://arxiv.org/html/2407.18141v1)). For two identical lamps, a printed AprilTag of 5-8 cm per lamp gives a deterministic ID (read range at 1080p is untested). For "on versus off", the most reliable signal is not vision: the program that toggled the lamp already knows its state, and Hue can stream real state over server-sent events. If pixels must decide, compare lamp-box brightness with the frame median per lamp against calibrated baselines, because auto-exposure defeats absolute thresholds (an inference; no source covers it). Run detection on a still crop at the pinch moment, not on every frame.

**Control.** Everything below is local and needs no cloud, and no end-to-end latency was measured for any of it. For a hackathon the quickest is WLED or Tasmota/Shelly: one HTTP call, no pairing. WLED takes `POST /json/state` with `{"on":true}` ([WLED JSON API](https://kno.wled.ge/interfaces/json-api/)); Tasmota takes `/cm?cmnd=Power%20On` ([Tasmota](https://tasmota.github.io/docs/Commands/)); Shelly Gen2 takes `/rpc/Switch.Set?id=0&on=true` ([Shelly](https://shelly-api-docs.shelly.cloud/gen2/0.14/ComponentsAndServices/Switch)). Home Assistant's REST API (`POST /api/services/light/turn_on` with a bearer token) is one front door to many brands if the team already runs it ([HA mirror](https://mintlify.com/home-assistant/core/api/rest-api)). Hue's CLIP v2 needs a bridge, an app key and HTTPS, with unconfirmed rate limits ([openHAB Hue v2](https://www.openhab.org/addons/bindings/hue/doc/readme_v2.html)). Matter is the slowest to set up and should be skipped. A demo lamp is an ESP32 with a WS2812 strip running WLED; for real mains lamps use a certified smart plug, never hand-wired mains. Event Wi-Fi often isolates clients, so use a phone hotspot or the team's own router (general experience, not sourced). Keep a small adapter layer, `set_light(id, on/dim/colour)`, with one backend per brand.

**Other MacBooks.** The notes found no source for telling one Mac from another, and identical models will fail on appearance alone. Their suggestions are inferences: a helper on each Mac shows an AprilTag or QR code carrying its hostname when asked, or flashes a unique colour pattern that the glasses can see, and the Mac in use is the one already running the hub. Controlling another Mac needs a helper process on it speaking the hub's WebSocket protocol; this was not researched and is the team's design decision.

## A spoken introduction needs a consented guest list and a push-to-talk band

**Command path.** The podcast host talks constantly, so always-listening intent detection will false-trigger. The notes' inference, which fits the kit's own pattern, is to arm the microphone with a band `tap` or `double-tap`, then call `speech.listen(band, 5)` in the main program (never in a handler), and pass the text to `ai.choose` with a whitelist of actions such as point_at, wide_shot and stop, with targets limited to enrolled names ([AGENTS.md](../../AGENTS.md)). Code must validate both action and target and never run model output directly. A regex or fuzzy match on "introduce|welcome|over to <name>" is a cheaper fast path. Deepgram streaming targets 300 ms or less, and Nova-3 keyterm prompting can bias recognition toward guest names ([Deepgram latency](https://developers.deepgram.com/docs/measuring-streaming-latency.mdx), [changelog](https://developers.deepgram.com/changelog/2025/2/12)); both are vendor claims. The notes' end-to-end estimate is 1.5-4 s (STT, LLM, recognition, motor), unmeasured. While the band microphone is on its LED is locked solid blue and everything it hears goes to Deepgram, so tell people nearby and keep the Deepgram key in an environment variable or an untracked `.env`, never in code or chat ([AGENTS.md](../../AGENTS.md), [docs/deepgram.md](../../docs/deepgram.md)). The band is findable only by exact name `Vexo-HACK-` plus the team's number, so the command path must use the team's number only.

**Finding and following the person.** For a closed list of two to four guests, ordinary face embeddings fit best: InsightFace `buffalo_l` (SCRFD detector plus ResNet50 recogniser) or dlib's `face_recognition` (128-D encodings, default tolerance 0.6) ([InsightFace model zoo](https://github.com/deepinsight/insightface/blob/master/model_zoo/README.md), [dlib](https://blog.dlib.net/2017/02/high-quality-face-recognition-with-deep.html)). InsightFace's weights are **non-commercial only**, and its own table shows uneven accuracy across demographic groups (for `buffalo_l`, 94.70 for Caucasian against 74.96 for East Asian on MR-ALL), so test on every guest and keep a human override. Enrol one to three consented frontal photos per guest, store embeddings locally, and at runtime accept a match only above a threshold with a margin over the second-best, otherwise answer "unknown". Podcast footage (angled faces, headphones, microphone arms) will be harder than LFW scores suggest. A VLM or open-vocabulary detector is the slow fallback for descriptions like "the man in the blue shirt", run once per command. After lock-on, detect people with YOLO11, track with ByteTrack or BoT-SORT (the latter has camera-motion compensation, which matters because the camera moves), bind the name to a track ID once, and steer with a PID loop and a 5-10% deadzone ([Ultralytics tracking](https://academy.ultralytics.com/courses/yolo-in-production/tracking-with-bytetrack-and-botsort), [rpi-deep-pantilt](https://github.com/timayy/rpi-deep-pantilt)). Convert pixel error to angle with `atan((x - cx)/f_x)`, where `f_x = (W/2)/tan(HFOV/2)`, verify by commanding a known pan step, and recompute per zoom level. Frame the face on the upper third, ease between people over 1-2 s, and add soft limits and a spoken "stop".

**Gimbal and camera.** Rank by feasibility, as the notes do. A PTZ camera speaking VISCA over IP (TCP 5678 or UDP 1259) or ONVIF is documented and language-neutral ([PTZOptics](https://docs.ptzoptics.com/articles/miscellaneous/misc-cameras/an-introduction-to-ip-control-&-scripting-for-ptzoptics-cameras), [ONVIF PTZ spec](https://www.onvif.org/specs/2512/ONVIF-PTZ-Service-Spec-v2512.pdf)). The OBSBOT Tiny 2 (pan plus or minus 140 degrees, tilt +30 to -70 degrees, 120 degrees per second) exposes standard UVC pan/tilt and an OSC interface through its desktop app, but its SDK and OSC address list were unreachable, and the working OSC example needs the OBSBOT Center app running ([specs](https://obsbot.com/obsbot-tiny-2-4k-webcam/specs), [community OSC script](https://github.com/M4ri002/OBSBOT-Tiny-2-lite-control)). An ESP32 with servos or a SimpleBGC controller with its documented serial API are the DIY routes ([SimpleBGC spec](https://www.basecamelectronics.com/files/SimpleBGC_2_6_Serial_Protocol_Specification.pdf)). Apple DockKit is Swift/iOS-only, limits motion calls to about two per second, and a developer reports its motor calls failing on an Osmo Mobile 8 ([DockAccessory](https://developer.apple.com/documentation/dockkit/dockaccessory.md), [Apple forum](https://developer.apple.com/forums/thread/821439)). Avoid DJI handhelds. ONVIF ContinuousMove has reported stop failures, so always send an explicit stop and keep a manual override. No command-to-motion latency was found for any device, so budget motor speed, not protocol delay.

**Consent and privacy.** Matching faces to names is biometric processing. Under GDPR it is special-category data needing an exception such as explicit consent, UK ICO guidance says never to assume consent from someone entering the field of view, and Illinois BIPA requires a written release and a published retention policy (secondary summaries only; not legal advice) ([ICO](https://cy.ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/lawful-basis/biometric-data-guidance-biometric-recognition/how-do-we-process-biometric-data-lawfully/), [GDPR Art. 9 summary](https://www.gdprregister.eu/articles/biometric-data-gdpr/)). The design rules follow. Enrol only guests who give written, specific consent naming the purpose (camera steering), where embeddings are stored, and when they are deleted. Store embeddings locally and delete them after the show. Match only against that list; never identify bystanders, audience or public figures, and give unknown faces "unknown" with no lookup. Log decisions, not faces. Do not send frames to a cloud VLM unless the consent covers that transfer. Prefer the biometric-free fallback where possible: bind names to seats ("guest left") or to a tracked person with a one-time host click or voice confirmation. The same rule applies to the glasses and the band: the Mentra camera light is always on while streaming ([camera streaming](https://docs.mentraglass.com/bluetooth-sdk/camera-streaming)), and the kit says to tell people before the microphone records and to stop when asked ([AGENTS.md](../../AGENTS.md)).

## De-risk in this order, each step with a fallback that still demos

The order below follows the notes' own sequencing, with the glasses stream test brought forward because it gates three of the four goals. Durations are guesses, and none of the steps has been tried on this team's hardware.

| Step | What to prove | Pass test | Fallback if it fails |
|---|---|---|---|
| 0. Setup | Ask for the team's band number, store it once as `TEAM_BAND`, develop on the pretend band (`transport="sim"`), then connect the real band from the Mac with the dashboard closed | `band.number` matches; 100 Hz motion and events logged | USB cable, or keep the pretend band |

## Conclusion

The research changes the question from "how do we make the glasses a live sensor?" to "which decisions can tolerate a slow, unmeasured one?". Only target selection, slow context and lamp or screen identification can. Triggers, release and the throw need the ESP32 and the band, and the Mac hub is what makes that division workable: it holds the band's single Bluetooth connection, serves WebSockets, stamps every message and writes the log that turns guesses into measurements. A single-channel EMG clench is also a better match for "squeeze like paper" than for pinch-to-click, so the squeeze demo is realistic even if the camera-based cursor ends up region-level only.

The most useful finding is a negative one: the evidence base for the hardest link, Mentra Live to Mac, is almost entirely documentation claims, so the team's first hours should produce a latency distribution, a capabilities dump and a go/no-go on RTMP. Every downstream choice (cursor mode, retrospective lookup, whether to keep the glasses at all or substitute a webcam) follows from that one number. For the gimbal, the cheapest ethical design avoids biometrics entirely by binding names to seats or a host click, and uses face embeddings only for guests who consented in writing.
